# サトシのセッションの引き継ぎ

2026-11-22 オーナー「クレジットの消費が高くなったら、またセッションの切替を提案して。今後も引き継ぐから、ルール化してスムーズに移行できるようにして」。同日「（古い定期作業は）止めてよいが、新規セッションに引き継ぎなさい。送り先も新しいセッションに変えてよい。これらもルール化して、引き継ぎ時に自動化しなさい」。

長い会話は、1回の返事ごとに全部を読み直すので高くつく。サトシの会話は区切りで新しいセッションに移し、担当（オーキド・ポケモン）と定期作業はそのまま使い続ける。
**ここは公開リポジトリ**。セッションの ID・金額は書かない（タイトルで探す）。

## 0. オーナーが先に許していること（引き継ぎのたびに聞かない）
新しいサトシが本物（オーナーが作ったセッションで、オーナーが「サトシを続ける」と書いている）なら、次は確認なしでやってよい:
- 前のサトシに結び付いた定期作業を、新しいサトシに同じ中身で作り直し、**前の物を止める**（消さない）。
- 担当への連絡の送り先を新しいサトシに変える。
- **担当へ**: サトシへの連絡は、題名がちょうど「サトシ」のセッションに送る（「引き継ぎ済み」と付いた古い物には送らない）。定期作業の文面を自分で書き換える必要は無い。

- 引き継ぎ以外で、定期作業・担当・シートを消す／止める／書き換えるのは、選択式で聞いてから（2026-11-17 ユーザー決定。月一の健康診断の文面にしか書かれていなかった）。
- 定期作業の文面を短く作り直すときは、古い文面の日付付きの決定を1つずつ、新しい文面か `.claude/rules/` に移したかを確かめる（2026-11-22 の省力化で、朝の報告から月曜の振り返り・入庫から出品への引き継ぎ・その日の予定が落ちていた）。

## 1. 切り替えを勧めるとき（今のサトシ）
- 長い作業が終わった区切りで `get_session`（session_id なし）を見て、`context_usage.used_tokens` が **30万を超えていたら**、返事の最後に1行で切り替えを勧める。話題が大きく変わるときも勧める。作業の途中では勧めない。
- 勧めるときは、同じ返事の最後に **「引き継ぎメモ」** を書く（次のサトシはこれを読む）:
  1. 終わっていない作業（PR 番号・URL・シート名）
  2. オーナーの返事待ち・対応待ち
  3. 後でやると約束したこと
  4. その日に決まったこと・指摘（`オーナーの考え方.md` に足した行）。**オーナーが言ったのに、まだ決まりのファイルに書いていない物が無いか**を最後に見る（会話は次のサトシには読めない。書いていない物はそこで消える）
- オーナーの手作業は「新しい会話を開いて『サトシを続ける』と書く」だけにする。
- **新しいサトシの会話は Opus 5.5 で作る**（2026-11-24 オーナー「次の新規セッションから、Fable ではなく Opus で作って下さい」。2026-11-23 夜の会話は、`.claude/settings.json` の model が Opus 5.5 なのに別のモデルで始まっていた＝クラウドの会話は、アプリで選ばれているモデルで始まり、settings.json では決まらない）。切り替えを勧めるときは、今のサトシが `create_session`（model は `claude-opus-5-5`、最初の文は「サトシを続ける」）で次の会話を作り、その会話へのリンクを引き継ぎメモと一緒に渡す。オーナーはそのリンクを開くだけ。オーナーが自分で新しい会話を開いたときは、引き継ぎの最初に `get_session` でモデルを見て、Opus 5.5 でなければ1行目でそう伝える（アプリのモデルの選び直しはオーナーにしかできない）。

## 2. 引き継ぐとき（新しいサトシ。「サトシを続ける」「引き継いで」と言われたら）
聞かずに全部やる。順番:
0. 最初に古物台帳「意思決定ログ」シートを全部読む（決まりのファイルに無い決定が残っている。2026-11-23）。
1. `list_sessions` でタイトルが「サトシ」の前のセッションを探す。`list_events`（kinds は assistant と user・最新の1ページ）で「引き継ぎメモ」を読む。メモが無ければ、最後の数往復を担当（general-purpose）に要約させる（自分で全部は読まない）。
2. `set_session_title` で、このセッションを「サトシ」、前のセッションを「サトシ（〜日付・引き継ぎ済み）」にする。前のセッションは消さない・アーカイブしない。
3. `list_triggers` で定期作業を見る。
   - **前のサトシに結び付いた有効な物**（月一の健康診断・期限付きの確認など）: 同じ名前・同じ時刻・同じ文面でこのセッションに作り直し、前の物は**止める（enabled=false。消さない）**。
   - **担当の定期作業**: 何もしなくてよい。宛先は ID ではなく「題名がちょうど『サトシ』のセッションを list_sessions で探す」と書いてある（2026-11-22 オーナー「毎回、サブセッションに書かないといけないのは手間です。自動化しなさい」で作り直した）。オーナーに担当のチャットへ書いてもらう作業は作らない。
   - **担当の定期作業を新しく作る・直すとき**: 文面にサトシの ID を書かない（上の形で書く）。文面は後から外から変えられないので、直すときはサトシが `create_trigger`（persistent_session_id に担当のセッション）で作り直し、古い物を止める。担当に書き換えを頼まない（担当のチャットの権限で止まる）。
   - **「ボタン依頼（サトシ）」**（AURORA コアの［依頼］→ サトシ）: ページは定期作業の ID を直接呼ぶので、毎回つなぎ直す。①同じ名前・同じ文面の時刻なしの定期作業を、このセッションに `create_trigger` で作る ②AURORA コア（Artifacts「AURORA コア」）を `Artifact` read で読み、`const TRIG` の「サトシ」の行を新しい定期作業の ID とこのセッションの ID に Edit で直して、同じ URL に publish する ③前の「ボタン依頼（サトシ）」は止めずに残す（呼ばれなくなるだけ）。ほかの担当の行は変えない。
   - **いつも使うページをこの会話に付ける**（2026-11-23 オーナー「チームと数字のグラフは最低でも紐付けろ」）: Artifacts の「AURORA コア」「aurora チーム」「aurora 数字のグラフ」の3つ。`Artifact` read で読み、中身を変えずに同じ URL へ publish する（開くだけでは付かない。AURORA コアは上の宛先の直しと一緒に）。公開の前に、写しを一度開いてエラーが無いことを見る。終わったら `get_session` の artifacts に3つあるか確かめる。
4. オーキドと担当の全員に、新しい宛先を `send_message` で知らせる（返事は不要と書く）。
   - 担当が前のサトシへ送ったままの確認・質問が無いかを、前のセッションの最後のページ（届いた担当からの文）で見て、拾う（2026-11-23。ピカチュウの確認が半日宙に浮いた）。
5. `CLAUDE.md` の「担当のセッションの探し方」と食い違いが無いか見る。
6. オーナーに表で報告する: 引き継いだ事・終わっていない作業・対応待ち・できなかった事。

## 3. 変えられないこと（2026-11-22 に確かめた）
- 担当のセッションの「親」は、作ったときのサトシのまま（アプリの親子の表示は付け替えられない）。紐付けは「報告先」と「タイトル」で行う。
- 定期作業の結び付け先のセッションは、後から変えられない（作り直す）。
- 定期作業の文面は、その定期作業が書き込むセッションからしか変えられない。
- **担当のセッションは引き継ぎのときに作り直さない**（2026-11-22 オーナー決定「今の形のまま」）。画面の親子の表示は前のサトシの下のままでよい。働き（報告・定期作業）は題名「サトシ」でつなぐ。
