# 利益計算のルール

- **費用は実績どおりに入れる（多めに盛らない）**（2026-11-21 ユーザー指摘「経費は高く見積もれば安心ではない。仕入れもしにくくなる、むしろその方が問題」）。費用を多めに見ると、利益が出る物まで買えなくなり、それ自体が損になる。費用は領収書・請求・明細の実額を、商品1点あたりに割って使う。実額が無い・分からない費用は、推測で上乗せせず、分かっていることと範囲を示してユーザーに決めてもらう。赤字仕入れは、相場の根拠の強さと判定の基準（利益・利益率）で防ぐ。
- 安い物の基準（2026-11-19 ユーザー決定）: 売値（送料込み）$99以下の物は、利益の基準を **4,000円以上** に上げる（利益率8%は同じ）。実績79件で $99以下の37件は1件平均344円しか残らなかったため（`config.toml` の `low_price_usd`・`low_price_min_profit_jpy`、`appraise.low_price_min_profit` / 拡張機能 `calculate`）。
- 入札判断の基準: 利益2,000円以上 **かつ** 利益率（売上＝eBay売値の円換算に対する割合）8%以上で**全体統一**（2026-11-17 ユーザー決定。落札を増やすため 2,500円・10% から下げた。安心ストアなどの例外なし。損益分岐を超える入札はしない。`tools/config.toml` の [judge]）。
- **ジャンクは出品者で分ける**（2026-11-26 オーナー「カメラのみを扱っている専門業者のジャンクはジャンクです。カメラ以外も扱っている総合業者や個人、コレクターのジャンクは、動作する可能性が高いです。それらのジャンクは狙います」「専門業者かどうかの判断は、全商品のうち、50%以上がカメラの場合は、専門業者とみなします」「専門業者のジャンクには入札しませんが、完動品や綺麗なものには積極的に入札します。本当に動く可能性が高く、綺麗な場合が多いからです」）: Mac が毎朝、ジャンクと ◎○ の出品者のページ（/seller/<userId>。robots.txt の Allow の形）で全出品数と「カメラ、光学機器」（auccat=23636）の出品数を数え、半分以上なら専門店（data/seller_kind.csv に30日。1回30人まで。検索結果の出品者名は伏せ字なので ID で分ける）。**専門店のジャンク → ×**。総合業者・個人のジャンク → ◎○ のまま「★ ジャンクは狙い目」。専門店のジャンクでない物 → ◎○ のまま「★ カメラ専門店」の印。毎朝の入札リストでジャンクを名指しで探す検索も足す（`appraise.junk_search_urls`。カメラのカテゴリ）。数えているのはカテゴリ「カメラ、光学機器」（双眼鏡なども入る）。まだ数えていない出品者は今までどおり（1日30人まで・拡張機能だけで見た新しい出品者は翌朝以降なので、それまでは専門店のジャンクも ◎○ で出ることがある）。「★ カメラ専門店」はジャンクと書いていない物すべてに付く。最初の選択式では「専門店は要確認」だったが、後の言葉「専門業者のジャンクには入札しません」で × にした。上限入札額・想定の売値は変えない（`appraise.check_junk_sellers`・`junk_seller_kind` / 拡張機能 `junkSellerKind`。テストは `test_trust.JunkSeller`）。下の「ジャンク表記は気にしない」は、出品者が分からないときの扱い。
- ジャンク表記は気にしない（届くまで分からないため）。割り引かず、ジャンクという理由だけでは要確認にしない。
- eBay 出品中の最安値から相場を出すとき: **送料無料の出品は出品額 − $30**、送料を別に取っている出品は出品額（商品代）そのままを、送料別の商品代として提示する。sold（売れた価格）も同じく、送料無料で売れたものは売れた額 − $30（2026-11-16 ユーザー決定。`active_free_ship_deduction_usd`。仮の相場は最安値）。
- 送料は販売価格から一律 $40 を差し引く（入札判断。2026-11-15 に $30 から変更。今から仕入れる商品は次の出品から送料 $40 を乗せるため）。出品中・販売済みの商品の見積もり（数字のグラフ）は $30（`listed_deduction_usd`）。eBay手数料: FVF実効12%（日本のセラーは落札手数料に消費税10%が乗った額で引かれる。2026-11-25 に取引明細と公式の料金表で確かめた）＋海外1.55%＋広告2.2%＋$0.44。円転ロス2%。消費税還付は含めない。オークレボ（発送代行）の手数料 1点 820円（SpeedPAK 540円＋海外発送手数料 280円）と梱包 300円を毎回引く（2026-11-21 ユーザー決定。`agent_fee_jpy`・`appraise.item_cost_jpy`）。関税は今は引いていない。11月の CPaSS・関税の請求を見てから送料 $40 を見直すか決める（2026-11-21 ユーザー決定。実額は knowledge/ の意思決定ログ）。自分からオークレボへ送るヤマトの集荷代も、商品1点あたり 250円を毎回引く（何点かを1箱にまとめて送るので、領収書の合計をその間に仕入れた商品数で割った額。ヤフオク・店舗とも。`forward_jpy`。2026-11-21 ユーザー指摘「1個あたりではない」で 1,200円から直し、同日「商品数で算出」で 250円）。
- eBay の$は**送料を除いた商品代（net・送料別）**で表示・入力する（2026-11-15 ユーザー指定。拡張機能・スマホのアプリ・毎朝のレポート）。相場データ（price_memo.csv など）と計算は送料込みのまま持ち、入力された net には送料 $40 を足して保存する。
- ジャンク表記も想定販売価格は割り引かない（2026-11-16 ユーザー指定で7割評価をやめた。`junk_price_factor = 1.0`）。説明文や商品名にはっきり書かれた光学難（カビ・クモリ・バルサム等）は × で見送る（修理しない方針。2026-11-18 ユーザー決定・おまかせ: 実績は光学難ありの平均利益が赤字。「カビ・クモリなし」のような打ち消しは除く。傷・ヤケは要確認のまま）。**例外: 軽いカビ**（2026-11-26 オーナー「小カビも2,3個ならNearMINTなので、入札しないわけではないが、鑑定表示の枠は、カビがないものと分けてほしい」→ 選択式で「軽いカビだけ別の枠」）: 小カビ・点カビ・カビ少し・カビ1〜3個 と書かれた物は × にせず、◎○ のまま入札候補とは別の「カビの記載あり」の枠に出す（上限入札額は同じ計算）。［◎○をまとめて開く］には入れない（写真で程度を見てから）。毎朝の予約リストでは10本に数えず、下に別の枠「カビの記載あり（写真で程度を確認）」で出す（消さない。`appraise.reserve_mold`）。「小カビ2,3個」「カビ2〜3個」の書き方も軽いカビ、「多少のホコリ」の「多少」は多いと読まない。カビ多い・クモの巣状・大きい・程度の書いていない「カビあり」と、クモリ・バルサムは今までどおり ×（`appraise.light_mold` / 拡張機能 `lightMold`。テストは `test_trust.LightMold`）。
- 根拠の強さを必ず示す: 自分の販売実績 ＞ Chatwork実績 ＞ 頒布会リスト ＞ 鑑定表(推定)。**販売履歴は自分の古物台帳に限らず、Chatwork の他の人の事例と頒布会も含める（頒布会も売れたものとみなす。2026-11-18 ユーザー決定）**。この3つが根拠なら「確認不要」（`SURE_TIER = 2`）、鑑定表・仮の相場は「確認してから」。
- 数値を変えたら `config.toml` を直し、`knowledge/意思決定ログ.md` に日付付きで記録する。クラウドからは古物台帳（元の台帳。2026-11-17 から1冊運用）の「意思決定ログ」シート（日付・決めたこと）に書けば、毎朝の `update_all.py` が Mac の md に追記する。
- 入札の記録（2026-11-19 ユーザー指摘）: 拡張機能の［入札した］と「入札結果」シートの max_bid は、**拡張機能が出した上限額（提示額）**。ユーザーが実際に入札した額とは限らない。負けた入札の分析では「上限額の何倍で落札されたか」と書き、「相場が上がった」「上限が低すぎた」と決めつけない（相場の見直しは sold を確かめてから）。
- オークファンで実際に入れた額と失敗コード（2026-11-24 オーナー「オークファンでの私の入札価格と、実際に落札された金額を取得できる？」）: Chrome でオークファンの「入札完了」の一覧（tools.aucfan.com/v2/snipe/item?type=close）を開くと、拡張機能が開いたページの分を ダウンロード/aurora_snipes_closed.csv にためる（読むのは開いたページだけ。入札・予約はしない）。毎朝 Mac が入札の記録に足す: my_bid＝**実際に入れた額**（max_bid＝拡張機能の提示額とは別の列）、bid_fail＝オークファンの失敗コード。失敗コードは3種類見つかっている（2026-11-24 オーナーの全521件）: 900010010・900010000＝「システムエラー。入札が適切に処理されませんでした。」／202＝「あなたの入札価格を上回る入札が行われました」。**bid_fail は記録するだけで、結果（落札・負け・確認待ち）は変えない**（同日訂正: 最終価格と照らせたシステムエラー11件のうち10件は、最終価格が入れた額より上だった。エラーの表示だけで「入っていれば勝てた」とは言えない。「入札が入っていないから落札できない」と決めつけない）。ブックマーク「入札完了を読む」（全ページを順に読んで同じ CSV を保存する。サトシがチャットで渡した物）でも同じファイルができる。落札された額は今までどおりヤフオクの出品ページから読む（final_price）。判定・上限入札額には使わない（`extension_aucfan.js`・`bid_results._merge_closed_snipes`。テストは `test_bids.py`）。システムエラーが出る原因は未確認。
- 答え合わせ（2026-11-24 オーナー「落札金額のデータも入札に活かしたい」→ 選択式で「答え合わせ＋10本」）: 毎朝、候補（◎○・入札した）のうち**上限入札額（提示額）以下で落札された出品**を、入札の記録の有無・入れた額・オークファンの失敗コード・その日の予約リストに出ていたか（reports/reserve_list_日付.csv から。残っていなければ「記録なし」）と一緒に古物台帳「Mac_答え合わせ」に送る（直近14日。`yahoo_results.review_csv`）。予約リストの行には「落札の中央値（この機種・直近90日）」を出す（`reserve_rows` の sold_stats）。**どちらも表示だけ**で、判定・上限入札額・並びは変えない（落札額はもう「勝ちやすさ」として並びに使っている）。読み方の注意: 「上限以下で終わった＝入れていれば取れた」ではない（落札者の上限は見えない）。商品名に難の語が無くても説明文に不良があることがある（付属品・ジャンクなどは外さずに印を付ける）。入れる額を落札額に寄せる案は採らない（予約入札は次点＋1段しか払わないので、下げても安くならず負けが増えるだけ。上げるのは損益分岐を超える）。
- 落札相場と入札の結果（2026-11-19 ユーザー「いくらで入札したかより、いくらで落札されたかが重要」）: `data/yahoo_results.csv` の final_price は**ヤフオクで実際に落札された額（市場の価格。ストアは税抜）**、max_bid は**拡張機能・入札リストが出した上限額（提示額）**で、実際に入札した額とは限らない。落札できたかは max_bid と比べず、古物台帳にそのオークションID・URLがあるかで決める（無ければ終了から `ledger_wait_days` 日は「確認待ち」→「負け」。入札0件で終わったら「流れた」で落札率に数えない）。落札相場は表示と分析だけに使い、判定・上限入札額・利益の計算には使わない（`yahoo_results.py`・`bid_results.judge_result` / 拡張機能 `yahooLine`）。**終わった出品のページは、ログインしていないと最終価格を見せず開始価格を出す**（2026-11-25。1円開始・入札26件で「1円」を落札額にしていた）。入札2件以上で価格が開始価格のままなら「落札額不明」とし、落札額の中央値・答え合わせ・負けた差に使わない（落札かどうかは今までどおり古物台帳で決める。`bid_results._item_state` の hidden。テストは `test_yahoo_results.test_hidden_final_price`）。
- 入札候補の並び（2026-11-18 ユーザー決定）: 売れ筋（販売履歴＝自分・Chatwork・頒布会のある機種。仕入値が分かる記録は、その仕入値から見て基準以上の利益が出ていたものだけ）と売値（送料込み）$99超を上に、$99以下は下に回す。同じ順位の中は終了が近い順。判定・上限額は変えない（appraise.py の `bid_priority`・`sold_hit`、拡張機能の `bidPrio`）。
- 状態の補正（2026-11-18 ユーザー決定・おまかせ）: 1ランク $10 の固定額をやめ、価格に対する割合にした。自分・Chatwork の販売実績で、同じ機種の状態違いの組から1ランクあたりの%を毎回推定する（3〜15%。組が5つ未満なら `condition_step_pct` = 8%）。美品は上限が上がり、並品は下がる。
- 売れ筋の機種の検索（2026-11-18 ユーザー決定）: 毎朝の入札リストに、売れ筋の機種を名指しで探す検索を利益の大きい順に30本足す（メーカー＋型の語。1本100件＝既定50件×2ページ。並べ替え・件数の引数は付けない＝robots.txt。`appraise.py --hit-searches 30`、`hit_search_urls`）。販売履歴のある機種を入札リストに多く出すため。
- 負けた機種・古い相場（2026-11-18 ユーザー決定）: 直近60日に競り負けた機種も、売れ筋と同じく名指しで毎朝探す（最大20本。`lost_models`）。90日以上直していない相場メモは、毎朝「Mac_未登録機種」に最大10件足し、夜の下調べで見直す（`stale_memos`）。登録は朝に選ぶだけ。
- Chatwork の販売価格（2026-11-18 ユーザー決定）: スクールの方針でだいたい送料 $30 込み。商品代（送料別）＝報告額 − $30 とし、うちは送料 $40 で出品するので、計算上の売値（送料込み）＝商品代 ＋ $40（`chatwork_included_usd`、`appraise.chatwork_gross`）。例: 報告 $169 → 商品代 $139。
- まとめ売り（2026-11-18 ユーザー決定）: セット出品は、区切り（＋ + 、 , ／ / ＆ & 「と」）で分けた中身ごとに相場を当てて合計する。型の語（焦点距離・型番）がある部分だけを中身とし、相場が見つかった中身だけを足す（見つからない中身は $0）。2点以上見つかったときだけ判定し、2点目からは送料（一律）・1注文の手数料・梱包を引く（別々に売る前提）。中身が分からないセットは今までどおり要確認（`set_part_titles`・`set_value` / 拡張機能 `setPartTitles`・`setValue`）。
- F値とボディの型番（2026-11-18 ユーザー指摘）: 「F2」「F3」のような整数だけの語は、**すぐ前**が数字・焦点距離・レンズ名（Nikkor・Zuiko など）なら F値、それ以外（「Nikon F2」「ニコン F3 50mm」の F3）はボディの型番とみなす。f/2・f1.4・1:2 は常に F値（`is_f_number` / 拡張機能 `isFNumber`。商品名の書き方の一覧は `判定ロジック.md`）。
- 以前の入札分析ファイルのリサーチ（2026-11-19 ユーザー決定）: 「リサーチ貼付」の品名・eBay 売値$・講師価格を、古物台帳「共有_リサーチ相場」経由で相場に使う（`data/research_prices.csv`、根拠「リサーチ（推定）」= tier 3）。講師価格があれば講師価格。売れた額か送料込みか分からないので、送料無料とみなして −$30 を商品代とする。鑑定表と同じく「確認してから入札」で、自分・Chatwork・頒布会の記録がある機種はそちらを優先。販売履歴（売れ筋）には数えない。
- 系統とマウント（2026-11-19 ユーザー決定）: 同じ焦点距離・F値でも別物は相場を当てない。系統の語（Zuiko Digital・M.Zuiko・Rolleicord・Rolleiflex）は片方にだけあれば別物。レンズのマウント（Canon EF・EF-S・EF-M・FD・FL・RF、Nikon Z と F〈Ai・AF・AF-S など〉、Sony FE と E、Fujifilm X と GF）は、両方の商品名でマウントの組が同じときだけ当てる。片方にマウントが書いていないだけでも当てない（要確認に回す。高づかみを防ぐ）。機種名・sold/now の検索語にも残す（`series_of`・`mount_of` / 拡張機能 `seriesOf`・`mountOf`）。
- Canon の L レンズ（2026-11-19 ユーザー指摘「L は大事」）: 「F1.2L」「F4 L」の L は系統の語として扱い、L と L なしの相場は当てない（片方にだけ L があれば別物）。機種名・sold/now の検索語にも「L」を残す。「EF 50- F1.2L」のように mm を書き忘れた焦点距離は 50mm とみなす（`canon_l` / 拡張機能 `canonL`）。
- レンズキット（2026-11-19 ユーザー指定）: 「レンズキット」「kit」の出品も、まとめ売りと同じく中身（ボディとレンズ）ごとに相場を当てて合計する（かっこの中も中身として分ける）。中身が2点見つからないときは今までどおり全体で照合。拡張機能の「相場が未登録の機種」では、セット・キットを1つの枠に中身ごとの行で並べ、それぞれ sold・now・全て開く・登録ができる（`KIT_RE`）。
- 勝ちやすさ（2026-11-19 ユーザー決定）: ヤフオクの終わった出品のうち、今の上限入札額以下で終わった割合（ストアは税抜にして比べる）を機種（model_key）ごとに毎朝出す（`win_score.py` → data/win_score.csv。直近90日・5件以上の機種だけ使う）。難あり語・まとめ売り・付属品・入札0件・上限の4割未満の安値は数えない。**1割未満の機種は入札リスト・拡張機能の下に回すだけ**で、判定（◎○×）・上限入札額・利益の基準（2,000円・8%）は変えない（`bid_priority` / 拡張機能 `bidPrio`。表示「勝ちやすさ 46%（直近12件）」）。記録が無い機種は今の並び・表示なし。
